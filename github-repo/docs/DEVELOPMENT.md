## 一、项目背景与动机

### 1.1 原多开器为什么不好用

对原 `多开器.exe` 做了反编译分析，结论：

- 原多开器对游戏窗口 **零样式改动**（不去边框、不改样式、不改客户区尺寸），只用最保守的方式管理窗口；
- 这正是它"鼠标精准、分辨率准确、不卡"的根本原因——大话2客户端（Java/AWT 系）对窗口客户区尺寸变化**极其敏感**；
- 我们自己先前花积分做的多开器不好用，是因为动了不该动的东西（样式/尺寸），触碰了客户端的雷区。

### 1.2 目标形态

浏览器式页签管理：

- 一个容器窗口，里面多个游戏"页签"；
- 页签条：各号名称、× 关闭当前号、＋ 开新号；
- 点击页签切换显示对应客户端；
- 主面板保留：实例列表、目录隔离启动、平铺、泄漏监控等。

### 1.3 语言选型

- 选择 **C 语言 + Win32 API**（WinLibs GCC 16.2.0 编译）；
- 理由：单文件 exe（C 版 43KB vs Python 打包 12.5MB）、无运行时依赖、可直接迁移到任何电脑使用；
- 编译命令统一格式：
  ```
  gcc -O2 -s -municode -mwindows -finput-charset=UTF-8 <源文件>.c -o <输出>.exe -lgdi32 -luser32 -ldwmapi
  ```

## 二、关键形态决策：真嵌入 vs 遮挡式

### 2.1 两种实现方式

| 方式            | 原理                                                       | 风险                                 |
| ------------- | -------------------------------------------------------- | ---------------------------------- |
| 真嵌入（原多开器疑似做法） | 去掉游戏边框（WS_POPUP），客户区直接并入容器                               | **必死**：客户区高度变化 39px，游戏画面错乱、鼠标上下不精准 |
| **遮挡式（最终采用）** | 游戏窗口零样式改动（只 SetParent + 平移），工具自绘标题栏 + 页签条**盖在**游戏原生标题栏上面 | 游戏完全无感知，可随时揭开验证                    |

### 2.2 实验定责（embed_test1 四步实验，用户实测）

| 步骤 | 操作                        | 结果                      |
| -- | ------------------------- | ----------------------- |
| 1  | 仅 SetParent（零样式改动）        | ✅ 一切正常                  |
| 2  | 加页签条、窗口整体平移 34px（尺寸不变）    | ✅ 一切正常                  |
| 3  | 去边框改 WS_POPUP（客户区变高 39px） | ❌ 鼠标上下不精准、画面多出一截        |
| 4  | 恢复                        | （AWT 销毁旧窗口重建，引出后面一系列问题） |

**结论（铁律）**：动大话2客户端，只允许 SetParent + 平移（不改尺寸不改样式），绝对不能去边框。

### 2.3 "为什么非要去边框"的疑问与回答

用户曾问：为什么一定要去边框才能实现多开效果？不能用 Java 写吗？

回答要点：

- 不需要去边框——遮挡式方案证明了可以完全不去边框实现同样的视觉与交互效果；
- Java 不适合：要写的就是操作 HWND 的窗口级操作，Win32 API 是正路；Java 起一个 JVM 只为摆几个窗口，得不偿失。

## 三、遮挡式方案演进（embed_test3 系列版本史）

### 3.1 架构总览（最终形态）

```
容器窗口（自绘蓝色标题栏 30px：可拖动 + —/× 按钮）
  ├── 游戏窗口（SetParent 进容器，含原生边框，只平移 34px，尺寸样式不变）
  └── 页签条 = 独立置顶顶层窗口（WS_EX_TOPMOST|TOOLWINDOW|NOACTIVATE，owner=容器）
        位置 = 容器客户区 (0, 30)，正好盖住游戏原生标题栏
```

**为什么页签条必须是独立顶层窗口**：曾尝试用容器内"兄弟窗口 + z-order 抢层"，失败——游戏（AWT）提升自己 z-order 的频率远高于我们，页签条反复被盖住。改成独立置顶顶层窗口后彻底解决。

## 四、问题全记录（现象 → 诊断 → 结论 → 方案）

### 4.1 游戏跑位（AWT 缓存屏幕坐标）

- **现象**：SetParent 后游戏自己挪回原屏幕位置，遮挡错位。
- **诊断**：AWT 内部缓存了屏幕坐标，SetParent 后按缓存值自我修正。
- **方案**：容器 WM_TIMER(3) 每 200ms 钉扎——检测到游戏偏离 (0, TBAR_H) 即按回。
- **配套**：实验器必须 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`，否则坐标差被 DPI 缩放系数放大。

### 4.2 页签条被游戏盖住（z-order 抢层失败）

- **现象**：一点标签标签就消失；游戏提升自己 z-order 更频繁。
- **结论**：容器内子窗口方案不可行。
- **方案**：页签条升级为独立置顶顶层窗口（TOPMOST|TOOLWINDOW|NOACTIVATE），SyncStrip() 每 200ms 按容器客户区 (0,TBAR_H) 的屏幕坐标同步位置。

### 4.3 ALT+E 等快捷键失效（跨进程键盘焦点）

- **现象**：嵌入后游戏内快捷键全部失灵。
- **诊断**：`SetFocus` 只在本线程消息队列内有效，跨进程无效。
- **方案（3g，实测有效）**：
  1. `AttachThreadInput(容器线程, 游戏线程, TRUE)` 焊接输入队列；
  2. 再 `SetFocus(g_game)`；
  3. 保险丝：容器把 WM_KEYDOWN/UP/SYSKEYDOWN/SYSKEYUP/CHAR 用 `PostMessageW` 转发给游戏子窗口；
  4. 触发时机：WM_PARENTNOTIFY、WM_ACTIVATE、嵌入完成时调用 AttachGameInput()。
- **注意**：恢复时必须 `AttachThreadInput(mt, gt, FALSE)` 解除焊接（3h 加了 DetachGameInput），否则游戏窗口激活状态悬空。

### 4.4 "恢复原样"游戏隐身（本项目最后卡点，已定位根因）

#### 现象演进

- 3d/3e：恢复后游戏消失，后台进程还在；
- 3f：恢复诊断显示旧句柄失效（样式仍含 WS_CHILD=0x06CA0000），"句柄失效且未找到新窗口"；
- 3g：FindPidCb 不再要求可见后，能找到新句柄了，但窗口"可见=1、位置(9,8)、尺寸1399x796、样式=94000000"却桌面看不见；任务栏有游戏标签但点不动关不掉（幽灵窗口）。

#### 根因确认（3h 诊断实锤）

- 恢复日志输出 `类=D3DFocusWindow 标题=D3DFocusWindow`；
- **D3DFocusWindow 是游戏 DirectX 渲染层的焦点辅助窗口，不是游戏主窗口**；
- 它恰好也是 WS_POPUP|WS_VISIBLE、尺寸与主窗口相同（1399x796），在"面积最大优先"的搜索里跟真主窗口打成平手甚至胜出；
- 于是我们把"游戏"切到了一个幕后辅助窗口上——真主窗口被晾着，任务栏标签自然点不动。
- **背景知识**：`SetParent(NULL)` 放回桌面时，Java AWT 会销毁旧 HWND 重建新窗口（可能起初隐藏），所以恢复必须按 PID 重找——但搜索条件必须严格。

#### 修复方案（3i）

1. **嵌入时**记录游戏主窗口类名 `g_origCls`（GetClassNameW）；
2. **恢复时两级匹配**：
   - 严格级：同 PID + 类名 == g_origCls（可见优先 + 面积加权）；
   - 兜底级：同 PID + 有标题，但**显式排除** `D3DFocusWindow`、`JavaAWT`、`MSCTFIME`、`Default IME` 等辅助类；
3. 切换新句柄时日志打印类名供核对。

#### 3i 实测结果（2026-10-11 12:14，本轮测试）——问题终局定性

- 严格类名匹配**成功命中**：`类=SunAwtToolkit 标题=theAwtToolkitWindow`；
- 说明游戏主窗口的类名本来就是 AWT 系（SunAwtToolkit），匹配逻辑没抓错人；
- 但用户截图显示：恢复后出现一个**白屏空壳窗口**（标题 theAwtToolkitWindow，有正常标题栏），游戏 D3D 画面没有跟随回来；
- **终局结论：不是搜索问题，是 AWT 重建的窗口本身就是残废的**——`SetParent(NULL)` 触发 AWT 销毁旧 HWND 重建后，新窗口只是一个空框架，游戏渲染层（D3D）不再挂接，无论怎么找窗口、怎么强制显示都无法还原游戏画面；
- **`SetParent(NULL)` 恢复路线正式判死**。


#### 补充实锤（2026-10-11 12:21 第二轮测试）——SetParent 是"单行道"

- 用户**直接关闭多开器**（点 ×，不做任何恢复操作），游戏同样变成白屏空壳窗口（theAwtToolkitWindow）；
- 原因：容器销毁时，跨进程子窗口被系统自动脱父子关系，效果等同于 SetParent(NULL)，一样触发 AWT 重建空壳；
- 用户手动 taskkill 清理了 3 个残留游戏进程（8076/7092/13308）；
- **结论升格：只要游戏被 SetParent 过，无论恢复、关闭多开器还是其他任何脱父子事件，游戏渲染都会死**。SetParent 架构是单行道——**零 SetParent 架构从"建议"升级为"必选"**。

#### 由终局结论导出的架构方向（下一步）

既然"嵌入后无法还原"，那么正确思路是**根本不做 SetParent**：

- 游戏窗口**永远是顶层窗口**，不改变父子关系（AWT 完全无感知，关闭多开器时游戏各自独立存活，天然"可还原"）；
- 容器退化为纯"外框 + 页签条"：用 SetWindowPos 把游戏窗口摆到容器客户区内（只平移/贴靠，不改尺寸不改样式——实验1/2已证明安全）；
- 页签切换 = 对各游戏窗口 SW_SHOW / SW_HIDE（对顶层窗口隐藏不会触发 AWT 重建，待实验验证）；
- 需要解决的新问题：游戏与容器的 z-order 协同（容器背景不能盖住游戏）、游戏被用户手动拖动时的钉扎、任务栏图标管理。

#### 幽灵窗口处理经验（运维备忘）

- 残留幽灵进程：`taskkill /IM 大话西游.exe /F`（PowerShell/CMD）；
- Git Bash 下参数要用双斜杠：`taskkill //PID 27964 //F`（单斜杠会被 MSYS 转义成路径）；
- 温和 taskkill（不带 /F）对隐身状态的游戏无效，直接用 /F。

### 4.5 恢复后 AWT 重建窗口的一系列连锁问题（历史记录）

1. 旧句柄销毁 → 必须按 PID 重找（3f）；
2. 新窗口起初隐藏 → 搜索不能要求 IsWindowVisible（3g）；
3. 辅助窗口冒充主窗口 → 类名严格匹配（3h→3i）；
4. **终局（3i 实测定性）**：即使精确找到 AWT 重建的窗口，它也只是白屏空壳，游戏渲染不回来——**"还原到桌面"在技术上不可行，不是工程问题**；
5. **生产版设计决策（因终局结论而强化）**：正式版页签多开器**不做 SetParent 嵌入**（见 4.4 架构方向），游戏窗口始终保持顶层身份；关闭页签 = 结束该游戏进程。
